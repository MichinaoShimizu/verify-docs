# 作業記録と保守報告

## 作業記録

各スキルは作業を始める前に、対象文書または違反一覧を自分専用の一時記録へ書く。
一時記録はリポジトリ直下の `.verify-docs/dist/` に置き、ファイル名を次に固定する。

| スキルID | 一時記録 |
| --- | --- |
| `verify-docs` | `.verify-docs/dist/verify-docs.work.md` |
| `dedupe-docs` | `.verify-docs/dist/dedupe-docs.work.md` |
| `tighten-docs` | `.verify-docs/dist/tighten-docs.work.md` |

`.verify-docs/dist/` がなければ作成する。作業中は一時記録を更新し、未確認項目を
`- [ ]`、確認済み項目を `- [x]` で表す。対象が複数スキルにまたがっても、他スキルの
一時記録は編集しない。実行が中断した場合も一時記録を残すため、作業状況と再開地点を
確認できる。

一時記録と `maintenance-report.md` に記載する対象ファイル・是正先・サイズ表のファイル名は、
すべて Markdown リンクにする。一時記録は未コミットの変更を示すため、表示するパスを
リポジトリルートからの相対パスとし、`.verify-docs/dist/` から解決するローカルリンクを
使う。例えば `AGENTS.md` は `[AGENTS.md](../../AGENTS.md)` と記載する。

既定の `dedupe-docs` または意味保持モードの `tighten-docs` が利用者の判断を必要とした場合は、一時記録に
`回答待ち` として候補と質問内容を残し、現在の会話で利用者に質問する。回答待ちの候補は
`- [x]` にせず、保守報告へ統合しない。利用者の回答後に対応と根拠を一時記録へ追記して
から完了として統合する。保守報告は未解決の判断を埋める場所ではない。

`tighten-docs` の自律圧縮モードと `dedupe-docs` の自律正本化モードで `回答待ち` を
作らない条件と記録する項目は、各スキルの `SKILL.md` が参照する自律モードの資料に従う。

一時記録には、作業単位、開始時刻、試行番号、対象一覧を含める。サイズ超過・重複・
リンク切れを `--json` で得た場合は、ファイル名だけでなく見出し階層と開始行も記録する。
AST の位置情報で修正箇所を特定できるときは、文書全体を1項目にしない。

```markdown
# 文書構造是正スキル

作業単位: 導入文書の構造是正
開始: 2026-09-13T23:45:02+0900
試行: 1

- [ ] [docs/deploy.md](../../docs/deploy.md) > デプロイ > 独自ドメイン（42行目）
- [ ] [docs/deploy.md](../../docs/deploy.md) > デプロイ > 初期設定（119行目）
```

日時は JST の ISO 8601 形式で記録する。確認を終えるたびに、項目へ日付と判断理由を
書き添える。

```markdown
- [x] [docs/deploy.md](../../docs/deploy.md) > デプロイ > 独自ドメイン（42行目） — 2026-09-13 /
      [docs/deploy-domain.md](../../docs/deploy-domain.md) へ移動し、元の位置をポインタ化
```

## 保守報告

| 項目 | 値 |
| --- | --- |
| 和名 | 保守報告 |
| 英名 | Maintenance Report |
| ファイル名 | `maintenance-report.md` |
| リポジトリ内パス | `.verify-docs/dist/maintenance-report.md` |
| 配布先パス | `.verify-docs/dist/maintenance-report.md` |

保守報告は、完了した1つの作業単位の実行履歴と最終検査結果を残す恒久記録である。
導入器は保守報告をコピーせず、各導入先で作成する。

## 保守報告への統合

実行対象の全スキルが完了したら、一時記録を
`.verify-docs/dist/maintenance-report.md` へ統合する。保守報告は完了後の正本であり、
作業中には書き換えない。単独実行では、その1スキルの完了時に統合する。

統合時は、実行したスキルごとに一時記録の対象・回答済みの判断理由・`### 最終検査結果` を対応する
スキルの和名セクションへそのまま移す。実行しなかったスキルのセクションは
`（未実施）` とする。形式と記入規則は
[保守報告の形式](maintenance-report-format.md)を参照する。

`maintenance-report.md` への統合を確認してから、その回に使った一時記録だけを削除する。
統合に失敗した場合や作業を中断した場合は削除しない。日時サフィックス付きの
保守報告や、別名の恒久ファイルを追加しない。

[保守報告の作業単位](work-record-lifecycle.md)に従う。

作業中と、文書変更を含む最初のコミットではローカルリンクを使う。外部から参照する
確定版の保守報告が必要な場合だけ、その変更コミットの後に、保守報告の
リンクを当該コミットのパーマネントリンクへ置き換える専用の更新コミットを作る。
GitHub なら `https://github.com/<owner>/<repository>/blob/<commit>/<path>` を使う。同じコミットを
指すリンクを、そのコミットに含めようとはしない。未コミットの変更、リモートリポジトリが
ない環境、またはコミットを特定できない場合は、古いコミットを指すパーマネントリンクを
作らず、ローカルリンクを残す。

## サイズ変更の記録

`tighten-docs` は、最初の試行で全対象ファイルの開始サイズを記録する。同じ作業単位で先に
`dedupe-docs` を実行した場合は、`dedupe-docs` の開始前のサイズを開始サイズとする（統合で
増えた文書を見落とさないため）。再実行では、
開始サイズを変えず、今回の最終サイズを記録する。`maintenance-report.md` には開始サイズ、
最終サイズ、開始時点からの削減バイト数、開始時点からの削減率を残す。削減バイト数は
`開始 - 最終`、削減率は `(開始 - 最終) / 開始 * 100` で計算し、小数第1位までとする。
削減バイト数と削減率は、正の値ほど削減、負の値ほど増加を表す。表は削減バイト数の
降順に並べる。直前試行との差分と、その理由を示す列は記録しない。
